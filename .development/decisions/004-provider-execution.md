# ADR 004 — Optional local provider execution

Status: Accepted for local implementation after the user's approval, 2026-10-13. Live provider acceptance and consumer spending remain separate.

## Problem and verified boundary

OLYMPOX 0.6.0-rc.1 already preserves provider choices, canon, reference bytes, task contracts, run attempts, stage readiness, generation declarations and reviews. `scripts/framework-core.mjs` returns task packages rather than calling providers. Its `job` field records one unresolved intent and requires reconciliation; it is not a durable execution queue. `scripts/stage-readiness-core.mjs` checks declared stage and pilot costs but does not reserve a shared concurrent budget. Existing Higgsfield transfer is a separate pinned Windows image transport, not a general generation adapter.

The user approved implementing the recommended provider abstraction in the reusable framework. Each installed studio supplies its own account, credentials, authorization and budget. This task implements reusable runtime behavior and synthetic verification; it does not produce a personal influencer or require the development user to fund a pilot.

## Decision

Add an optional dependency-free local executor and a BytePlus adapter alongside the existing core. Keep Node 22+, ordinary private studio files and built-in HTTP/crypto/filesystem APIs. Preserve the current Higgsfield default, existing providers, captured workflows and historical bytes. Installation remains offline and does not authenticate, configure consumer credentials, generate, train or publish.

The executor owns request preparation, immutable input snapshots, durable intent, queue state, local concurrency, reservations, status reconciliation and exported files. The adapter owns the actual provider schema, accepted model/input combinations, authentication at request time, estimates, submission/status requests and sanitized result metadata or bytes. Neither component approves identity or final media. Selene prepares and executes the selected stage through this boundary; existing canon and Têmis review remain responsible for acceptance.

Use `scripts/provider-execution.mjs` as an independent public CLI. Supported operations are preparation, explicit submission, readonly local jobs/budget inspection, explicit status queries of the original external job, export, budget configuration and cancellation of a queued local job. Status can record provider observations; it is not an entirely readonly command. A local cancellation must not claim that it cancels, refunds or reconciles an accepted external request. No installer, studio diagnosis or help command starts a worker or contacts a provider.

The local executor API is `prepareJob(root, request, {driver})`, `submitJob(root, id, grant, {driver, outputKey, fetch})`, `pollJob(root, id, {driver, outputKey})`, `exportJob(root, id, {fetch, outputKey})`, `reconcileJob(root, id, receipt)`, `cancelJob(root, id, provenance)`, `dispatchQueue(root, {driver, outputKey, fetch, maxJobs = 1})`, `setBudget(root, value)`, `getBudget(root)`, `listJobs(root)` and `readJob(root, id)`. `readProviderInput(root, relative)` reads bounded private descriptors. Optional `fetch` defaults to the platform transport. `outputKey` is an in-memory 32-byte Buffer or a function `(medium) => Buffer`; the CLI derives it from the original credential using a domain-separated SHA-256 operation, rather than requesting or storing another key. Explicit dispatch drains already authorized work; preparation or installation does not start it. CLI `status` queries the original accepted video job when applicable; `readJob`/`listJobs` are local inspection. Final CLI syntax is documented in the public guide and tested against actual help.

The initial BytePlus adapter lives in `scripts/providers/byteplus.mjs`. Its factory is `createBytePlusProvider({fetch, credentials, region, timeoutMs})`, exposing `capabilities()`, `credentialFingerprint(medium)`, `validate(request)`, `estimate(request)`, `submit(request, {signal})` and `getStatus(receipt, {signal})`. Credentials contain separate `apiKey` and `speechApiKey`. The adapter validates provider input/output schemas and decodes responses without writing studio records; the executor retrieves and persists media. The injectable transport exists for deterministic fixtures, not as a public production authorization bypass. This bounded implementation supports BytePlus in `ap-southeast-1` and its allowlisted API/CDN routes; another provider requires explicit adapter and core trust/validation integration, not just a new provider token.

## Request and identity contract

The public descriptor supplies `schemaVersion`, `characterId`, `purpose` (`reference` or `production`), `medium`, explicitly selected `provider` and exact `model`, a local `promptPath`, `parameters`, ordered `references`, `hasSpeech`, declared nonsensitive `destination` and optional/null `runBinding`. Job identity is generated during preparation. Reference entries have exact `referenceId`, `path`, `sha256`, `bytes`, `kind`, `role` and `order`, with optional `providerRole`; supplied digests/sizes are checked against actual local files. Image/audio references use exact inline bytes; remote substitutions and local video-reference bindings are refused in this increment. Prompt/reference snapshots, parameters, normalized driver payload/endpoint and relevant governance hashes become part of the immutable request scope. Preparation captures `providerContractHash`; dispatch compares it again so changed defaults or schemas cannot reuse an old grant. Unsupported parameters or capability combinations are rejected explicitly rather than silently dropped.

`reference` purpose supports initial candidates and draft voice without pretending that a canon has been approved. `production` binds the existing approved character, identity version, canon hash and preserved snapshot/reference bytes. The executor rechecks relevant source/context before dispatch and preserves its captured snapshot thereafter. Provider IDs, temporary URLs, training identifiers and expiry are transport bindings, never replacements for character identity or canonical files. Changing provider, model, prompt, parameters, references, destination or canon creates a new prepared request/job; old receipts, reviews and history are not overwritten or inherited as approval.

Speech has an explicit scope. A silent canon cannot dispatch speech. Existing speaking video production must actually bind and submit its selected approved audio reference through a supported route. Preset TTS is only `purpose: reference` with MP3 output and no audio conditioning references; it can generate a draft vocal sample but does not establish cloning or preservation of an existing voice. TTS production stays pending. If a selected API cannot accept the canonical vocal attachment, production remains pending; it cannot silently substitute a preset or regenerate a new canon. Generated video audio, consistent timbre and lip-sync remain subjects for listening and full audiovisual review.

BytePlus image/video/TTS support is scoped to the documented routes actually implemented and tested. An image or video endpoint does not establish access to TTS, voice cloning, identity training or every account model. Real portrait and trusted-asset restrictions, original-output/account conditions and expiration must be exposed as limitations and revalidated for each applicable stage. Fictitious external canon acceptance is a consumer pilot question. Do not recreate or transform a character to evade an input rejection.

## Persistence and external lifecycle

Keep job/request snapshots, reservations, reference bindings, receipts and exported private media in ignored installed-studio state. The shared ledger is `work/provider-execution/state.json` under an exclusive lock; per-job snapshots and receipts belong to the bound character's `executions/provider-jobs/<id>/` so its existing backup includes that history. Reject unsafe paths, another character's inputs, links/junctions, oversized inputs/responses and conflicting output destinations before writes. Preserve actual bytes as new files and record their hashes. Use atomic replace/create operations. Private state is excluded by both package source selection and installed-tree/export verification, not merely by `.gitignore`.

Persist the applicable grant, exact request hash and budget reservation before the first external submission. A queued job can be claimed once under the executor lock. Record `submitting` before the workflow bridge and HTTP POST. Capture known provider/request IDs and sanitized status evidence after a response. Process interruption, transport timeout or ambiguous submit response becomes unresolved/uncertain. After restart, an explicit status operation queries the original video job when its identity is available; absence of an ID or one empty list result cannot prove non-submission. An uncertain POST is never automatically repeated, routed to another provider or refunded locally. A character's uncertain/submitting predecessor blocks another paid attempt.

Status and export are explicit bounded operations; there is no background daemon, automatic polling/backoff or request-rate service. A caller may repeat a failed read/status/download without submitting new generation, while respecting actual provider quotas. A failed or rejected generation requires a distinct request/job and applicable authorization; it remains included in cost history. Queue concurrency and bounded dispatch count are local controls and must not be presented as provider quotas discovered from the account. A complete provider status does not establish local export, asset approval or workflow completion.

Accepted result metadata and original asynchronous IDs are persisted before staging media files; export uses a durable manifest before output writes and checks staged/orphan/exported hashes for safe exact recovery. Synchronous image/TTS has no supported original-job query: interruption after result metadata but before the first media staging write can leave a known outcome/reservation without recoverable local output bytes. Export remains pending on supported original-provider/manual recovery. The executor must not regenerate automatically or claim complete byte recovery for every crash window.

The runtime remains usable offline: missing credentials, provider capability, inputs, applicable grant or sufficient budget produces actionable pending/refusal before a paid request. Consumer credentials are supplied separately through the private process environment and passed to the adapter in memory. Nonsensitive region/account labels are caller declarations unless a verified route actually discovers identity; labels do not prove account ownership. Do not serialize authentication headers, keys, raw provider errors, plaintext signed URLs or credentials into job snapshots, logs, package files or character backups. Original remote output locators are stored as AES-GCM ciphertext; recovery requires the original credential-derived `outputKey`. Preserve shared ledger and character history together for continuation; a character-only backup contains receipts but does not reconstruct the queue/budget ledger or credentials.

## Financial boundary

Use an atomic studio/project budget ledger with per-job reservations and character attribution. The initial ledger supports USD only, not credits or automatic currency conversion. Distinguish estimated price, authorized maximum, reserved maximum and observed actual charge. Refuse dispatch when an applicable numerical reservation cannot fit the remaining budget. Unknown cost reserves the grant's whole numerical maximum. Estimated billing is a separate mode requiring explicit `acceptEstimatedCost` in the scoped grant; an estimate or caller-supplied maximum cannot be presented as a provider-enforced charge cap. The hard local ceiling constrains allocation through the executor, not the external invoice.

Reservations and intent must be persisted conservatively under one shared lock. A crash between durable records retains the reservation until recovery/reconciliation, rather than freeing money or redispatching automatically. Unknown actual charge retains the reserved maximum. Actual cost is settled only through explicit matching billing reconciliation, never by guessing an invoice from returned token counts. No missing field becomes zero. Exported jobs can still have unresolved financial reconciliation. Record rejected attempts and summarize consumption by job, character and project. Local limits cover submissions made through this executor; provider hard limits, external account use and variable billing remain separately documented constraints.

## Existing workflow interoperability

The independent executor produces traceable results for the existing readiness/run/asset operations. An explicitly supplied `runBinding` invokes existing readiness/start checks before POST and synchronizes the original external intent/outcome idempotently after ledger persistence. Exact stage model, normalized parameters, input set/roles/order and sanitized route/tool/module must match. It does not replace a captured workflow contract or complete its generation/review task automatically. A provider job receipt proves that job's observed status, not full `stage-readiness-v1` feasibility or human review. Existing media completion/registration/seal/review procedures remain applicable. Unresolved existing submissions must be reconciled before another attempt or route.

The current `mediaProviders` map stays compatible and defaults to Higgsfield. A future per-stage/multiple-provider contract can be additive after this bounded implementation; adding a functioning BytePlus driver is not grounds to change every medium's default or claim intelligent model selection. Selection begins with explicit capabilities and user method/provider choices.

## Acceptance, rollout and reversal

Verify exported public entrypoints with synthetic studios and a controlled HTTP stub: exact requests/attachments; image, asynchronous video and bounded HTTP TTS responses; credentials absent or redacted; status/export; interruption and uncertain POST; unsafe paths and output conflicts; budget concurrency and conservative recovery; canonical visual/vocal binding; historical files; installation/package privacy. Run `npm.cmd run verify` and `node .development/verify-aiox.mjs`, then the actual archive-derived independent installed-studio flow. Tests do not establish live model access or identity quality.

A consumer's separate authorized pilot must demonstrate exact approved external canon acceptance, original-byte export, stable facial/body/voice identity, complete inspection, actual costs and reuse constraints before BytePlus becomes that studio's primary provider. No personal pilot or paid call is part of the framework implementation task.

Reversal selects the previous provider for a new explicit request/attempt. Existing BytePlus jobs keep their original adapter available until reconciled and exported; returning to Higgsfield does not resubmit them. Preserve canon, media, snapshots, seals, budgets and historical attempts. Do not downgrade new private records into old schemas or rewrite approvals. Keep a reviewed earlier framework artifact available. Live pilot, market comparison, automatic model routing, cloud scheduling, distributed workers, voice cloning and provider training are separate follow-ups rather than implicit acceptance claims.

## Consequences

OLYMPOX gains actual reusable API execution while preserving its offline core and identity governance. HTTP abstraction does not guarantee provider/reference portability, billing parity or equivalent model results. The conservative reservation and uncertain-outcome rules can leave work pending and funds locally held; that is preferable to an unrecorded second charge. Implementation effort is bounded by the documented adapter modes and local worker; distributed orchestration is intentionally deferred.
